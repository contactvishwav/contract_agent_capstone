# Capstone Remediation — Consolidated Summary

*A retrospective of the full arc: inherited state → correctness bugs → real LLM extraction → enterprise-readiness remediation → live end-to-end verification → closing the README's remaining "future enhancement" gaps → a final real-browser verification → a production-readiness audit → a real GCP deployment → live-deployment hardening and an honest in-app Documentation page → the Supervisor Agent rebuilt for real → a bug live verification found that no test, mocked or live, ever had → closing the risk-category accuracy gap → real credential provisioning (org invites, Google OIDC SSO, TOTP MFA) → a same-night audit that found and closed a live cross-tenant leak plus two fully-backend-but-frontend-dead features → real Gemini-based search re-ranking, a resource-fit decision made by direct measurement, and a second live cross-tenant leak found and closed as a prerequisite for it. Every claim below is grounded in a commit hash, a file:line, or a benchmark results file — this document does not restate the aspirational claims in `README.md`/`docs/RESUME_WRITEUP.md` (or, as of §12, the frontend's own Documentation tab) without checking them against the code.*

## 1. What was inherited

The repository's own marketing copy (`README.md`, `docs/RESUME_WRITEUP.md`) claimed an "enterprise-grade" multi-agent system: 11+ specialized agents, a Supervisor pattern with "quality gates, error recovery, and A-F grading," a standardized MCP interface "with full data isolation and tracing," "explainable AI reasoning," "95%+ accuracy," "100% alignment with company standards," and "reducing legal review time by 70%." None of these claims had been checked against running code before this engagement began.

What was actually true, verified by reading the code:

- **Stubbed extraction.** `LLMClauseExtractor`, `LLMCUADClassifier`, and `ClauseDetectorTool` all had stubbed `_parse_llm_response()` implementations that returned `[]` regardless of input — `ClauseDetectorTool` didn't call the LLM at all. Locked in by a regression test (`test_stubbed_llm_parsers.py`, commit `66fb146`) before it was fixed, specifically so the eventual fix would be provably a fix rather than a silent behavior change.
- **Three parallel orchestration systems, not one.** The traditional LangGraph workflow (`IntelligenceOrchestrator`), the planning agent (`PlanExecutionEngine`, the actual default via `use_planning=True`), and `SupervisorAgent` (reachable only via the separate `POST /api/supervisor/workflow/execute` route) all exist independently. `RetryManager`/`CircuitBreakerManager` are only ever invoked inside `SupervisorAgent._execute_step_with_protection` — the actual default analysis path has zero reference to either class. The "quality gates" and "error recovery" advertised in the README exist, but not on the path that runs by default.
- **Broken MCP tool.** `fetch_contract_metadata` called an async repository method without `await`-ing it, so it always returned an unawaited coroutine that failed `json.dumps()` on every call. Existing tests used `MagicMock` instead of `AsyncMock`, which meant the bug was invisible to the test suite (fixed `e6c0eb1`).
- **Broken Supervisor wiring, two layers deep.** `SupervisorAgentFactory`, `PolicyWorkflowOrchestrator`, and `PolicyWorkflowSupervisor` all constructed `SupervisorAgent` with the wrong argument count — it was never successfully instantiated, likely crashing `POST /api/policies/upload` on every call (fixed `96f7250`). Fixing construction surfaced two more never-exercised bugs in the same file (a nonexistent `AuditEvent` class, a `ContentValidator` signature mismatch), fixed in the same commit. Even after construction was fixed, neither orchestrator class ever calls `self.supervisor.coordinate_workflow(...)` — the quality-gate/retry/circuit-breaker machinery is no longer *broken*, it's simply **never called**, on the one route that was fixed to construct it correctly.

This picture — stubbed extraction, disconnected orchestration systems, a crashing MCP tool, and dead-on-arrival Supervisor wiring — is the actual starting point this whole engagement worked from, not the README's description of it.

## 3. Phase 1 — real LLM extraction

`e6553cb` replaced all three stubs with a single `LLMExtractionService` using Gemini structured output against a verified 41-type CUAD taxonomy (cross-checked against the `theatticusproject/cuad-qa` dataset, which also fixed a duplicate and a wrong category name in the old `CUAD_CLAUSE_TYPES` constant). Offsets are computed deterministically by searching the source text for the LLM's claimed `extracted_text`, not trusted from the model — `start_offset == -1` signals text that couldn't be located verbatim (a hallucination-risk flag, acted on later in §4). The 6,000-character truncation that had been silently dropping late-appearing clauses was removed entirely.

|---|---|---|---|
| Document Name | 1.00 | 0.99 | 0.99 |
| Parties | 1.00 | 0.95 | 0.98 |

## 4. P0–P3 — enterprise readiness remediation

This phase followed a from-scratch, file:line-grounded audit (`docs/ENTERPRISE_READINESS.md`), rating 9 domain-specific areas — explainability, accuracy, tenant isolation, reliability, scalability, observability, data integrity, testing/deployment, and cost — against what a legal/compliance team actually needs (defensibility, traceability, tenant-safe confidentiality), not a generic SaaS checklist. All 9 areas started 🔴 or 🟡; the punch list below is ordered by that audit's own priority.

### P0 — severe risk, low-to-medium effort

1. **RBAC default-to-ADMIN bug** (`backend/governance/rbac.py:56-59`). The code's own comment claimed "default to VIEWER for safety" — it actually returned `UserRole.ADMIN` on a missing `X-User-Role` header, a live privilege-escalation path granting full permissions including delete rights to any unauthenticated/misconfigured request. Fixed `2cc284f`.
2. **Cross-tenant read/delete path in `PolicyRepository`.** `get_policy_by_id`, `_get_policy_rules`, `update_policy_version`, `delete_policy` had zero `tenant_id` filter in their Cypher. Combined with bug #1, this was a *confirmed-reachable* exploit chain, not theoretical: `policy_id` is generated as `f"policy_{tenant_id}_{timestamp}"` (target tenant derivable from the ID itself), and two of the four methods were live behind real routes — `GET /{policy_id}` and `DELETE /{policy_id}` (`backend/api/policy_api.py`), gated only by a permission check that the RBAC bug let anyone bypass by simply omitting a header. All four methods tenant-scoped in `9771ee2`; delete/update also fixed to correctly report failure instead of always returning `True` when a tenant-scoped match finds nothing.
3. **`get_intelligence_status`/dashboard hardcoded `"default-tenant"`** regardless of caller — fixed to use the real caller's `tenant_id`, `b58931d`.
4. **`ChainOfThoughtAgent._risk_assessment_chain`'s `overall_risk` `NameError`** — referenced a variable never assigned, guaranteeing failure whenever CoT risk assessment ran. Fixed by computing it as the max severity-derived score across violations; a second bug (the success path never included a `pattern` key) surfaced and was fixed in the same pass. `39bf98c`.
5. **`AuditLogger.get_audit_trail`/`ErrorTracker.get_error_statistics` retrieval**, flagged by the original audit as confirmed-broken via failing tests. Investigation found no bug in the actual retrieval logic — both failures traced to a bare `MagicMock` from an unrelated test file's guard leaking into the shared Neo4j singleton (its default `__iter__` silently yields nothing), a collection-order artifact, not a real defect. Fixed by giving both tests a proper fake graph simulating real `MERGE`/`MATCH` semantics. `b4606d8`. Suite: 5 failed / 61 passed / 1 skipped / 1 error, down from 8/42/1/2.

### P1 — severe risk, medium effort

6. **`tenant_id` required, not defaulted**, on upload/analysis routes (`contracts.py`, `document_upload.py`, `enhanced_document_upload.py`) — previously silently defaulted to `"default-tenant"` on omission, letting a request read/write another tenant's bucket unnoticed. No real authenticated-identity layer exists to verify a *claimed* `tenant_id` belongs to the caller (see §6), so this scoped down to the buildable half: reject the request outright (422) rather than default. `ae7d400`, `test_tenant_id_required.py` (8 affected routes, git-stash-verified).
7. **Audit trail wired into the real analysis path**, threading `contract_id`/`tenant_id` end-to-end through *both* orchestration paths (previously dropped one layer below `analyze_contract_by_id`, never reaching either), instrumented once at the shared tool layer (`ClauseDetectorTool`, `PolicyCheckerTool`, `RiskCalculatorTool`, `RedlineGeneratorTool`) rather than duplicated per orchestration path.
8. **Clause-linked violations/risk**: a stable, deterministic `clause_id` (contract+type+offset derived, not random) threaded through `PolicyCheckerTool`'s violations and a new `critical_issue_details` field on `RiskCalculatorTool` (additive — the existing `critical_issues: List[str]` shape was left untouched since two frontend components render it directly).
9. **Honest partial-failure state**: `RiskCalculatorTool`'s except path no longer fabricates `50.0`/`"MEDIUM"`; `_generate_redlines`'s except path no longer marks `is_complete: True` on failure; `PlanExecutionEngine` tracks per-step `node_status` instead of always reporting `processing_complete: True`; the API surfaces both honestly instead of a hardcoded `analysis_complete: True`. Items 7-9 landed together as `2dd078e` (shared architectural prerequisite). Suite: 84 passed / 5 pre-existing-unrelated failed / 1 skipped, up from 69/5/1.

### P2 — medium-term

10. **Ungrounded-clause flagging**: `start_offset == -1` (Phase 1's hallucination-risk signal) was computed but never acted on. `ClauseDetectorTool` now sets a `grounded` flag per clause, threaded through violations/risk as `clause_grounded` and surfaced in the API response — flagged, not excluded, so a human reviewer can still see it but knows not to trust it at face value.

Items 10-11: `7c6ecc6`, 10 new tests, suite 95/5/1 (up from 88).

## 5. Live end-to-end verification

Everything above was validated by a mocked test suite. This section is deliberately separate, because a mocked suite proved insufficient on its own — it required a real pass with actual API endpoints, live Neo4j/Redis, and real Gemini calls to find what it structurally could not.

### The mocking audit came first, because the "everything's mocked" assumption was false

Before running anything live, an audit of `backend/tests/` (`bafe79d`) found two files silently riding on pytest's collection order rather than genuine isolation:

- `test_pattern_integration.py` had **no `Neo4jGraph` patching at all**. `TestChainOfThoughtAgent` transitively constructed a real `Neo4jGraph()` (via `ChainOfThoughtAgent._risk_assessment_chain`'s lazy `PolicyRepository` import), and `TestReACTAgent` made a **real, unmocked `ChatGoogleGenerativeAI().invoke()` call** whenever `GOOGLE_API_KEY` was set — failures were swallowed, so the test "passed" regardless, but the call was genuinely made. Both only worked because an earlier-alphabetical test file's mock happened to still be cached in `sys.modules`; run either class in isolation and it hit real infrastructure.
- `test_rbac_integrated.py` had zero mocking at all (`from backend.main import app` transitively builds a real `Neo4jGraph()` the same way).
- `backend/shared/cache/redis_cache.py`'s module-level `cache = RedisCache()` singleton always attempted a real `redis.from_url(...).ping()` on import; whether a test got the `InMemoryCache` fallback was environmental luck, not a deliberate choice.

Fixed by wrapping both files' imports in the standard `Neo4jGraph` patch (with `.query.return_value = []` explicitly configured — a bare mock's `.query()` isn't iterable, which would make `PolicyRepository.get_applicable_policies` re-raise and silently flip assertions), injecting a fake LLM into `ReACTAgent.clause_tool`, and adding `backend/tests/conftest.py` to patch `redis.from_url` at module scope for the whole suite. Verified both files pass in isolation with `GOOGLE_API_KEY` unset and `NEO4J_URI` unreachable — proving the collection-order reliance was actually gone.

### What the live walkthrough confirmed working

Against real Docker-composed Neo4j/Redis and the real Gemini API (no mocking in the request path):

- **Real encryption, genuine ciphertext.** A direct `cypher-shell` query of `c.full_text` on a live-uploaded contract returned base64-looking AES-256-GCM ciphertext — confirmed unreadable, not a mocked assertion.
- **Real caching preventing redundant calls.** Re-running analysis on the same contract showed `total_calls` incrementing with genuine `cache_hits` for the clauses that had succeeded the first time (0 new real Gemini calls for those), while the 2 clauses that had failed a real 429 on the first run — correctly *not* cached, since a failed call never reaches the cache-set step — made fresh real calls on the second run and succeeded.
- **Real cross-tenant isolation.** The same contract ID requested with a different tenant's `tenant_id`, on both `GET /status` and `POST /analyze`, returned a clean 404 on each — not a mocked assumption.

### The 4 real bugs the live walkthrough found that a 211-test, all-passing suite did not

1. **`PolicyEvaluationService.evaluate_clause` silently swallowing real failures into a false clean result.** A genuine `429 RESOURCE_EXHAUSTED` during a live analysis run produced `intelligence_status: "completed"`, `risk_level: "LOW"`, `violations_count: 0`, with a `"success"` audit entry — because `evaluate_clause`'s `except Exception: return []` was indistinguishable, to every caller upstream, from "the model genuinely found zero violations." Fixed (`d163822`) by making `evaluate_clause` raise instead of swallow, `PolicyCheckerTool._run` catch per-clause and track `failed_clause_ids`, and both orchestration paths propagate an honest `"partial"` node status through to `processing_complete`/the persisted `intelligence_status` (now `"completed_with_errors"` when appropriate).
2. **Two separate Neo4j `DateTime` serialization leaks**, beyond the one initially found in `AuditLogger.get_audit_trail`: `GET .../status`'s `last_updated` field (`contract_intelligence.py`) and `ErrorTracker.get_recent_errors`'s `timestamp` field (reachable via `GET /api/audit/errors/recent`) both returned a raw `neo4j.time.DateTime` object, which FastAPI's default JSON encoder can't serialize and instead dumps as nonsensical `__dict__` internals (`"_Date__day": -2`). Found via a broad, deliberate search (not just the two flagged instances) and fixed with one shared helper (`serialize_neo4j_datetime`, `shared/utils/utils.py`) applied consistently at all three call sites, rather than a third inline copy of the same check. `18f84ab`.
3. **Unbounded LLM timeout/retry behavior.** An overnight benchmark run hung for **~3 hours** on a single clause-extraction call before finally raising "The read operation timed out" — no 429, no quota message. Investigation found `get_default_llm()` already had `request_timeout=120` configured; empirically proved (via a real socket that accepts a connection and never responds) that this timeout genuinely fires within its configured window when the process stays running. The likeliest explanation is the machine/session suspending mid-request — no in-process timeout mechanism, of any kind, can fire *during* a full process suspension, since no code executes at all until the OS resumes it. Closed the remaining real gap found along the way regardless: `llm_manager.py` and both `document_processing_service.py` files had no timeout/retry cap at all, unlike `get_default_llm()`. `35574b3`.

**The structural point**: a mock that always returns a canned successful LLM response cannot, by construction, distinguish "the policy check ran and genuinely found nothing" from "the policy check never actually ran." This is not a coverage gap that more mocked tests would have closed — it's a category of bug that is invisible to any test where the LLM call itself is stubbed out, because the entire bug *is* what happens when a real call fails. That is why this needed a live pass with a real, sometimes-failing API in the loop, not a broader mocked suite.

### Auth story rewritten for real JWTs; the walkthrough below reflects it

The walkthrough above still describes how P0–P3 behaved under the old auth mechanism — `tenant_id` as a caller-supplied query parameter and `X-User-Role` as a caller-supplied header, both trusted at face value. That mechanism is gone. Every route that used to read either of them now depends on `get_current_identity` (`backend/governance/auth.py`), which validates a signed JWT and is the *only* source of `tenant_id`/`role` from that point on. Repeating the walkthrough today looks like this:

1. **Register, then get a token.** `POST /api/auth/register` with `{"username", "password", "tenant_id", "role"}` creates a real account — bcrypt-hashed password, stored in Neo4j (`backend/infrastructure/user_repository.py`), a real `User.username` uniqueness constraint behind it. `POST /api/auth/token` with `{"username", "password"}` now verifies those credentials against that stored hash and only *then* returns a signed `access_token` (HS256, `JWT_SECRET_KEY`, 24h expiry) carrying the account's own `tenant_id`/`role` — not whatever a caller asks for. Every other route trusts the signature, not the caller's word. (Registration is deliberately self-service and minimal — no admin-provisioning UI exists yet, so this is currently the only way an account gets created at all; §8 has the honest scope of what this isn't yet.)
2. **Use it as a bearer token on everything else.** `Authorization: Bearer <access_token>` on uploads, analysis, status, search, policy, and audit routes. The old `?tenant_id=` and `X-User-Role` mechanisms are not read anywhere anymore — passing them has no effect at all, verified directly by `test_status_with_valid_token_ignores_caller_supplied_tenant_id_query_param` (`test_tenant_id_required.py`), which sends a request with a *different* `tenant_id` in the query string than the token carries and confirms the query value never reaches the Cypher params.
3. **Cross-tenant isolation is now identity-backed, not just parameter-backed.** The earlier walkthrough's "different tenant_id returns 404" claim was true, but under the old mechanism that was still a caller-supplied value being trusted — proving isolation *given* an honest caller, not against a dishonest one. `test_jwt_auth.py`'s `RealCrossTenantIsolationViaTokenTests` closes that: a genuinely valid, correctly-signed token for tenant B, used against tenant A's real contract_id, gets a clean 404 — not because tenant B typed the "right" id, but because there is no longer any field in the request tenant_id can come from except the token's own verified claim.
4. **`POST /analyze` is now asynchronous.** It returns `202` with `{task_id, status: "PENDING", status_url}` immediately and enqueues a real Celery task (`backend/tasks.py`) instead of blocking on the full multi-clause-extraction-plus-policy-evaluation pipeline in-request. `GET /tasks/{task_id}/status` polls real Celery task state (`PENDING`/`STARTED`/`SUCCESS`/`FAILURE`), and a task that fails mid-pipeline surfaces as a real `FAILURE` state with the underlying error message — not a silently swallowed exception. Only this one operation moved to Celery; `batch-analyze` and the read-path routes (search, status, policy, audit) stay synchronous, since they don't have the same multi-LLM-call runtime that justified the move.

Nothing else about the P0–P3 findings above changed — the encryption, caching, and honest-partial-failure behavior described in this section were re-verified against the new auth layer, not re-tested from scratch.

## 11. GCP deployment: e2-micro + Neo4j AuraDB + Caddy

A real deployment target, chosen and built out (`docs/DEPLOYMENT.md` has the full step-by-step): a GCP e2-micro Compute Engine VM (Always Free tier), Neo4j on AuraDB Free replacing the local `docker-compose.yml` Neo4j service, GCP Secret Manager as an optional secrets backend, and Caddy for automatic Let's Encrypt TLS.

- **`GCPSecretManagerKeyProvider`** (`backend/infrastructure/encryption.py`) implements the existing `IKeyProvider` interface, selected via `KEY_PROVIDER=gcp` — `EnvKeyProvider` stays the default everywhere else (local dev/CI completely unaffected). `validate_production_key()` is provider-aware: a misconfigured GCP provider (bad project id, missing IAM permission) hard-fails at startup by actually calling `get_key()`, not just checking an env var's presence. 15 new tests.
- **`docker-compose.prod.yml`** (separate file — `docker-compose.yml` stays dev-only) — no local Neo4j (`NEO4J_URI` points at Aura via required, fail-closed env vars), every service on the `production` image target, `restart: unless-stopped`, and `mem_limit`s sized from real measurements against the actual production images (not estimates): backend 246MiB idle, worker 236MiB idle at `--concurrency=1 --pool=solo` (the default would fork `os.cpu_count()` full copies — not viable on this VM), redis capped at `--maxmemory 150mb`, nginx frontend 7MiB, Caddy 13.5MiB. Also carries `image:` tags alongside `build:` so the same file supports both "build here" (dev machine) and "pull there" (the VM itself never runs `npm run build`/`uv sync` — confirmed too heavy for e2-micro's 1GB/burstable-vCPU budget).
- **Caddy chosen over nginx+certbot** for TLS, after comparing empirically (not just cited figures): Caddy idle ≈13.5MB RSS (60MB image) vs. certbot alone at 186MB. The deciding factor was operational surface area, not memory — Caddy gets automatic issuance/renewal/HTTP→HTTPS-redirect from a ~10-line Caddyfile with zero extra containers, while nginx+certbot needs a shared ACME-webroot volume, a renewal scheduler, and a reload hook (the classic way these setups silently expire certs is forgetting that last step). Caddy sits as a new, thin layer in front of the existing `ui` service — `frontend/nginx.conf.template` is completely untouched. `{$DOMAIN}` gates automatic HTTPS: a real domain gets a genuine Let's Encrypt cert with zero extra Caddyfile directives; unset falls back to plain `:80` so the stack is testable before DNS is ready. Verified against the real `caddy:2-alpine` image (`caddy validate`, plus a real Caddy→nginx→frontend round trip over an actual Docker network) — both the fallback and real-domain paths confirmed to activate/not-activate TLS correctly.
- **Resource fit: confirmed, but tight.** Sum of `mem_limit`s (backend+worker+redis+ui+caddy) ≈ 844MB, leaving ~180MB for the OS + Docker daemon on e2-micro's 1GB — workable given the tuning above, with a 2GB swapfile recommended in the runbook as a safety margin against transient spikes, not a substitute for the limits being right-sized.
- **A real, pre-existing blocker found and fixed along the way**: measuring the frontend production image required actually running `docker build --target production ./frontend` for the first time in this whole engagement (`docker-compose.yml`'s dev target only ever ran `vite dev`, which doesn't type-check). All fixed for real, not suppressed — verified via the actual `npm run build`, a real production Docker image build, and a running container serving the actual app. Full backend suite unaffected throughout (391 passed / 0 failed / 1 skipped).
- **Neo4j AuraDB connectivity — since completed.** *Was:* `docker-compose.prod.yml` and the runbook were ready for it, but the actual live connectivity test against a provisioned Aura instance was pending real connection details. *Now:* a real live pass ran end-to-end against the actual deployed public URL — register, login, upload, async Celery analysis, real Gemini-derived results, logout — finding and fixing 2 more real bugs along the way: `enhanced_document_processing_service.py` called `.invoke()` (sync) on a LangGraph agent whose `store_contract` node is `async def` (LangGraph's real error for this, "No synchronous function provided," was caught only by reading the actual response body, not just the HTTP status); and the frontend's Alpine-based Docker image's healthcheck used `http://localhost/...`, which Alpine's musl-libc resolver returns `::1` for before `127.0.0.1` — nothing listens on the IPv6 loopback, so the healthcheck failed with a false "Connection refused" that never reproduced in local Docker Desktop testing. ## 13. The Supervisor Agent, rebuilt for real

The Documentation tab's "Supervisor Agent" section (audited alongside §12's other findings) still described the orchestration system removed in §8 as dead code — `SupervisorFactory`, `QualityManager`, a message bus, a per-request-fresh circuit breaker that could never open, "99.9% uptime" — none of which existed anymore. Rather than correct the copy a second time, this was rebuilt for real: `POST /api/supervisor/workflow/execute` now does what the tab claims, built in 4 phased steps, each with its own regression tests and full-suite run — the same discipline this engagement has used for every other multi-part build.

Design principle stated up front and held to throughout: reuse what's real rather than duplicate it (the circuit breaker from §12, the audit trail, the honest partial-failure/`node_status` reporting from §4 item 9, the hallucination tracking from §10 item 12), and only build a genuinely new mechanism where a real gap exists — not to complete a checklist. Two items from the tab's original claims were explicitly *not* built and are documented as deliberate omissions, not gaps: a "Switch" recovery strategy (falling back to a different LLM provider) is a real, separate, larger decision — cost/quality trade-offs, needs another provider's key configured — left for a future pass, not faked; and a generic message bus was rejected outright — a pub/sub abstraction with exactly one real publisher and one real subscriber isn't a message bus, it's a disguised function call, and the real Redis pub/sub channel built in step 3 below exists because it solves an actual problem, not to check an architecture-diagram box.

1. **Circuit-breaker-aware extraction status + A-F quality grading** (`149251e`). The grading rubric itself (`backend/agents/supervisor/quality_grader.py`) is a deterministic A-F function built entirely on signals already computed by `PlanExecutionEngine` — `node_status`, `processing_complete`, per-clause `grounded`/`confidence_score` — not a new measurement, and not a resurrection of the deleted `quality_scorer.py`, whose grade was computed and never gated on anything (§8's original finding). 25 new tests. ## 14. The planning path had silently never completed — found by live verification, not a test

This is the most significant finding of the whole live-deployment-hardening pass, and it deserves to be told on its own rather than as one line in §13's step-4 entry.

**What the bug was.** `IntelligenceOrchestrator._analyze_with_planning` — the method that runs whenever `use_planning=True`, the default at every layer of this application including the frontend, which never overrides it — never called `workflow_tracker.start_workflow()`. `PlanExecutionEngine.execute_plan`, at the end of every real run, unconditionally calls `workflow_tracker.complete_workflow()`, which computes `datetime.now() - self.workflow_start_time`. With `workflow_start_time` still `None`, every single real invocation of the planning path raised `TypeError: unsupported operand type(s) for -: 'datetime.datetime' and 'NoneType'` — after all of that run's real steps (clause extraction, policy check, risk assessment, ...) had already executed successfully. The root confusion: `start_agent`/`complete_agent`/`error_agent` (used throughout `_analyze_with_planning` to track individual agents) and `start_workflow`/`complete_workflow` (the overall workflow timer) are two different pairs of methods on the same tracker object — the former were called correctly throughout; the latter's "start" half was simply never called at all. `execute_plan`'s own comment even asserted the opposite of what the code did: `# Don't reset workflow tracker - planning agent already started it` — a claim that was never true.

**Why every prior verification missed it.** `_analyze_with_planning`'s own `except Exception` block caught this `TypeError` and transparently fell back to `_analyze_traditional`, the older LangGraph-workflow path — which *does* call `start_workflow()` correctly and completed normally. The fallback's output is a structurally valid, plausible-looking analysis result: real clauses, real violations, a real risk score. The only observable difference is `node_status`'s key names (the traditional workflow's `"clause_extraction"`/`"policy_checking"`/`"risk_calculation"`/`"redline_generation"` versus the planning engine's own `"extract_clauses"`/`"check_policies"`/`"assess_risk"`/`"generate_redlines"`) — a detail nothing in this engagement's test suite or any prior live-verification pass (§5, §7, §11) had reason to assert on, because both shapes look like a real, successful analysis. This bug therefore silently downgraded every real analysis run in this entire engagement — through Phase 0-3's full test suite, the §5/§7 live end-to-end passes, the production-readiness audit, and the GCP deployment's own live verification — to the fallback path, with zero hard failures anywhere to notice.

**How it was found.** Not from a written test. Building the Supervisor rebuild's quality-grading and SSE-progress instrumentation (§13) gave a concrete reason to watch a real live run closely — polling `GET /workflow/{id}/status` after triggering a real analysis, the response showed `"quality_grade": {}`, `"analysis_method": None`, and `node_status` keys that didn't match `PlanExecutionEngine`'s own step-type values. That mismatch was the tell. Reading the worker's real logs for that exact task_id showed all 6 planning steps completing successfully, immediately followed by `❌ AGENT FAILED: Autonomous Planning Agent — Error: Planning failed: unsupported operand type(s) for -: 'datetime.datetime' and 'NoneType'`, then `Planning agent failed... falling back to traditional workflow`. The bug was invisible in the API response (a valid-shaped `SUCCESS` result) and only visible in raw worker logs from a real run — exactly the kind of evidence a mocked test, or even a live pass that only checks the final response shape, cannot produce.

**The fix.** One line — `workflow_tracker.start_workflow()` added at the top of `_analyze_with_planning`, mirroring the traditional path's own already-correct convention — plus 2 regression tests (`7b5ef5f`), git-stash-verified to reproduce the exact reported `TypeError` against the pre-fix code. Full suite: 459 passed / 1 skipped / 0 failed. Re-verified live immediately after: the same `POST /workflow/execute` → `GET /status` → SSE-stream sequence described at the end of §13 now genuinely runs the planning path (real `node_status` keys, a real `quality_grade`, a real `analysis_method`) instead of the traditional-workflow fallback.

**The broader lesson.** This is the second time in this engagement that live testing found something structurally invisible to automated tests — not a coincidence, a pattern. §5 found `PolicyEvaluationService.evaluate_clause`'s `except Exception: return []` swallowing a real `429 RESOURCE_EXHAUSTED` into a false-clean `"completed"` result with `violations_count: 0` — indistinguishable, to every caller and every mocked test, from "the model genuinely found nothing." This bug has the identical shape: a silent `except`-and-fallback that produces a plausible, valid-looking result, where the *only* thing distinguishing a real success from a silently-degraded one is a detail nothing was asserting on. §5 drew the conclusion for that first case: "a mock that always returns a canned successful LLM response cannot, by construction, distinguish 'the policy check ran and genuinely found nothing' from 'the policy check never actually ran.'" This finding extends that same conclusion one level up the stack: mocked *and* even repeated, real, live end-to-end testing can still validate the wrong code path entirely, for an entire engagement, if a silent fallback exists between the code path being tested and the code path actually running — because a fallback's whole job is to produce a plausible result, which is exactly what makes it invisible to any verification that only checks "did I get a plausible result back." The mitigation that actually worked, twice now, was not more tests of the same shape — it was live instrumentation detailed enough to make the *specific* execution path observable (real worker logs, in both cases), not just its output.

## 15. Closing the risk-category accuracy gap: root-caused, not guessed

§4 item 12's headline finding — 0.32 average F1 across the 36 risk-relevant CUAD categories, 20 of them below 0.30 F1 — was measured but not fixed at the time. This pass closed it for real, following the same root-cause-before-fix discipline as every other accuracy finding in this document (§3, §4a).

**Root-cause, from data already in hand.** Every one of the 20 weak categories was individually diagnosed from the real per-contract predictions already stored in the 497-contract checkpoint (`extraction_eval_checkpoint_risk-categories-flash-lite-497.jsonl`) — zero new LLM calls needed for diagnosis, the same technique §4a used for the Expiration Date finding. Verified, not assumed: no generalizable matcher bug existed this time (unlike §4a's date-parsing case) — every "found something, didn't match" case inspected across the highest-unmatched-ratio categories showed the model's prediction and CUAD's gold span were genuinely different sentences about the same topic, not the same content in a matcher-unfriendly format. `evaluate_extraction.py`'s matcher was left unchanged; that honest negative result is reported in `docs/EVALUATION.md` §4c rather than a fix being forced where the data didn't support one.

The 20 categories split into three real, distinct failure modes, each getting a different treatment in `backend/agents/llm_extraction_service.py` (full table, before/after numbers, and per-category rationale in `docs/EVALUATION.md` §4c, not duplicated here):

- **Group A (precision fix, 2 categories)** — Third Party Beneficiary and Change Of Control: the model found *a* clause, but the wrong one (a disclaimer instead of a grant; a definition instead of the operative clause). Fixed with a one-line disambiguating hint per category (`_CATEGORY_HINTS`).
- **Group C (recall gap, 10 categories)** — the model already found real examples but under-recalled. Same one-line-hint treatment.
- **Group B (near-zero engagement, 8 categories)** — the model essentially never attempted these at all (0-1 true positives *and* near-zero false positives across all 497 contracts — not wrong guesses, no guesses). A second, narrower, example-backed LLM call (`FALLBACK_CATEGORIES`/`_run_fallback_pass`), fired only when the primary pass found none of these 8 — mirroring the deterministic-table-vs-LLM-reasoned split already used in `PolicyEvaluationService` (§4 item 11), adapted here as "broad pass vs. targeted narrow pass."

Two real gaps found and closed live while running this: the benchmark script itself needed a `_RpmLimiter` (new in `evaluate_extraction.py`) to stay under the per-minute cap, and `_extract_with_transient_retry` to distinguish a genuine per-day quota wall (still fails fast, correctly) from a transient 503/timeout/per-minute-window (now retried automatically instead of ending the whole run). 18 of the 20 targeted categories improved, several substantially (Joint Ip Ownership +0.388, Unlimited/All-You-Can-Eat-License +0.300); 1 stayed flat at 0.00; 1 got honestly worse (Source Code Escrow, −0.089, reported not hidden — see `docs/EVALUATION.md` §4c). Worth noting: an earlier 243-contract partial measurement had reported 2 categories (Covenant Not To Sue, Most Favored Nation) as regressions — both turned out to be real improvements once measured on the fuller 492-contract sample, confirming that read was sampling noise, not a real effect.

89 new tests, full details in `docs/EVALUATION.md` §4c. `docs/EVALUATION.md`'s risk-relevant F1 figure and the in-app Documentation tab's headline number were both updated to the new, 492/510 figure of 0.43.

## 16. Real credential provisioning: org invites, Google OIDC SSO, TOTP MFA

§8/§9 had flagged this as the honest remaining gap since the JWT migration: "Registration is minimal and self-service, not a full IdP — no org-admin invite flow, no SSO, no password reset, no MFA, no email verification." Before building, a design report was written and approved first (org invites vs. an ad-hoc admin-creates-users flow; OIDC via Google specifically, chosen because it doesn't lock into one vendor and a real, testable IdP already existed to build against; TOTP over SMS-based MFA, since SMS needs a paid provider and TOTP needs nothing external; Resend for transactional email, chosen after checking real, current free-tier terms rather than assuming from memory) — the same propose-then-build discipline as the Supervisor Agent rebuild (§13).

**POST /api/auth/register is now bootstrap-only** — the actual fix for the vulnerability the fully-open version had (any unauthenticated caller could self-register into any existing `tenant_id` with `ADMIN`). It may still create the first user of a brand-new tenant (so the system doesn't need a manual DB seed step to exist at all); a second registration attempt against an already-provisioned tenant is rejected (`TenantAlreadyProvisionedError`/403, checked *after* username-uniqueness so a genuine duplicate-username attempt still reports the more specific error). From here on, joining an already-provisioned tenant requires a real invite.

**Org invites** (`backend/infrastructure/invite_repository.py`): admin-only (new `Permission.MANAGE_USERS`), scoped to the caller's own `tenant_id` — read from the verified JWT, never the request body, since there's nowhere in the request to smuggle a different tenant through. Tokens are `secrets.token_urlsafe(32)`, sha256-hashed at rest (a high-entropy random token, not a low-entropy password — bcrypt's adaptive cost buys nothing here, a real primitive-choice distinction documented in the module itself), single-use enforced atomically in Cypher (`MATCH...WHERE used_at IS NULL...SET`), 7-day expiry. Accept creates the account with `tenant_id`/`role` read from the server-side invite record, never client input — the actual vulnerability fix. Real transactional email via Resend, verified live (Aug 2026 free-tier terms checked directly rather than assumed: 3,000/month, no credit card, sandbox sender can deliver to the account owner's own verified address without a custom domain — enough for real end-to-end verification, not enough yet for inviting arbitrary teammates without a domain).

**Google OIDC SSO** (`backend/governance/oidc.py`, `backend/api/sso_api.py`): a real authorization-code + PKCE flow against Google's actual discovery document, token endpoint, and JWKS — not a mocked IdP. Uses `joserfc` for JWT/JWKS verification, not `authlib.jose` — caught live (that module prints its own deprecation warning pointing at `joserfc` as the replacement) before building on a deprecated API. SSO is invite-gated by design: a verified Google identity alone can never self-provision into a tenant — first login requires a matching, unconsumed invite; only then is `(sso_provider, sso_subject)` linked for future logins. `invite_token` rides through server-side `state` (Redis), not a raw callback query param, since Google's redirect only ever echoes back `code`+`state` — a real design correction caught before it shipped, not after (Google would never have echoed a smuggled extra param at all).

**TOTP MFA** (`backend/governance/mfa.py`): `pyotp`-based, secret encrypted at rest via the existing `FieldEncryptor` (recoverable, unlike a password hash — the same "two different problems, two different primitives" reasoning `infrastructure/encryption.py` already establishes), 10 single-use bcrypt-hashed backup codes issued at enable time, two-step login (`POST /token` returns an `mfa_required` challenge when enabled; `POST /mfa/verify` completes it). Real anti-replay: rejects reusing a 30-second time-step even within `pyotp`'s own valid window. **A real bug found and fixed during live testing**: `pyotp.TOTP.at()` takes a Unix timestamp, not a raw step/counter number — the anti-replay logic's first version validated codes against the wrong second entirely (interpreting a step count like `59534967` as a timestamp — the year 1971), caught only by live end-to-end testing against the real deployed Neo4j, not by any unit test (the bug was in the *arithmetic*, not the logic being tested).

`governance/auth.py` gained one necessary, backward-compatible addition: an optional `username` JWT claim. ## 18. Search re-ranking: a real second stage, a second live cross-tenant leak found building it, and an honest evaluation gap

Requested as a production-grade addition to semantic contract/clause search (currently: embed query → Neo4j vector index → return top-K directly, no re-ranking), matching the same rigor already established for every other external-dependency call in this codebase — not a minimal bolt-on.

### Resource-fit investigation, measured before choosing (not assumed)

The two real candidates: a local cross-encoder (`sentence-transformers`) or Gemini. Installed `sentence-transformers` in an isolated venv, loaded `cross-encoder/ms-marco-MiniLM-L-6-v2` (the standard lightweight reranking model), and ran one real batched inference (query × 30 candidates, matching the intended candidate-pool size) while tracking real process RSS: bare Python 13.2MB → after `import torch` 188.7MB → after loading the model 159.1MB (post-GC) → **after one real batched inference, 208.8MB**. Torch itself is 533MB on disk.

Against the real e2-micro production VM's already-committed budget (`docker-compose.prod.yml`: backend 300m/worker 280m/ui 40m/caddy 64m/redis 160m = 844MB of 1GB, §11) — adding ~209MB to either container would push total system commitment past 1000MB, leaving as little as 15-20MB for the OS on a box the deployment's own docs already flag as needing its full documented swapfile margin. **Decision: Gemini for re-ranking** — zero incremental deployed memory (no new library loaded; `langchain-google-genai` is already resident in both containers), reuses the exact circuit-breaker/semaphore/usage-tracking infrastructure already protecting every other Gemini call, at the honest cost of real network latency per call (mitigated by batching every candidate into one request) and a small real, tracked API cost.

### A second live cross-tenant leak, found as a direct prerequisite

Investigating exactly where to wire re-ranking in found that `POST /api/contracts/search/enhanced` — the real, frontend-facing search endpoint the actual Search page calls (`enhancedSearchApi.ts` → this route; distinct from the LangChain-tool-facing `EnhancedContractSearchTool`/`get_contracts_multi_level` path in `enhanced_contract_search_tool.py`, which already had tenant scoping) — had **zero tenant isolation** across all four of its search levels. `SearchParams` (`backend/domain/search_entities.py`) had no `tenant_id` field at all, and the route only used `requires_permission(...)` as a bare `dependencies=[...]` gate, discarding the resolved identity entirely. Any authenticated caller in any tenant — VIEWER included, since `Permission.ANALYZE` is held by every role — could search and read every other tenant's contracts, clauses, sections, and party relationships. The exact same class of bug as §17 finding #1, in a different, previously-unaudited file. Building re-ranking on top of this would have meant a re-ranker faithfully scoring and re-ordering leaked cross-tenant data — cannot honestly claim re-ranking preserves isolation "as strictly as existing search" when existing search had none, so this was fixed first, not deferred:

- `SearchParams` gained a required `tenant_id` field; `enhanced_contract_search.py`'s four routes now resolve it from `identity.tenant_id` (the validated JWT), never a client-supplied value — there is no `tenant_id` field on any request body to even attempt smuggling one through; `EnhancedSearchService._search_all_levels` threads it through its own internal fan-out; all four `search_strategies.py` strategies (`DocumentSearchStrategy`/`ClauseSearchStrategy`/`SectionSearchStrategy`/`RelationshipSearchStrategy`) now filter by `c.tenant_id = $tenant_id` in their Cypher, unconditionally, not just when other filters are present.
- **Found and fixed in passing**: `ClauseSearchStrategy` returned raw AES-256-GCM ciphertext as "clause content" — `clause_repository.py` encrypts `Clause.content` at rest (redact-then-encrypt, §4 item 21), but this raw-Cypher search path bypassed that repository's decrypt-on-read entirely. Would have made clause-level re-ranking score ciphertext against a real query — meaningless. Verified `SectionSearchStrategy`'s `s.content` needed no equivalent fix (genuinely unencrypted at write, confirmed by reading `section_repository.py`, not assumed from the Clause case).
- **Found and fixed in passing**: `/search/clauses`, `/search/sections`, `/search/relationships` each computed a real `SearchResult` and never returned it — always sent an empty `200` regardless of what the search found.
- Proven two ways: `test_vector_index_search.py` extended with tenant-scoping Cypher/param assertions for all four strategies (git-stash-verified: 6 of 6 new/changed assertions genuinely fail pre-fix) plus a new clause-decryption test; new `test_enhanced_search_tenant_isolation.py` proves it through the real FastAPI route with two real tenants and a graph that would actually leak if the fix were wrong (not a bare `MagicMock`, which returns the same canned data regardless of `tenant_id` and so can't distinguish a real fix from a fake one) — 4 of 4 new tests also git-stash-verified to fail pre-fix.

### `RerankerService` — matching every established external-dependency pattern

`backend/agents/reranker_service.py`: retrieve a wider candidate pool (`RERANK_POOL_SIZE = 30`, up from the normal `RERANK_TOP_K = 10`) from the already-tenant-filtered vector-index query, one batched Gemini structured-output call scores the whole pool's relevance to the query in a single request, return the re-ranked top 10.

- **A dedicated `RERANKER_CIRCUIT_BREAKER`** (`shared/reliability/circuit_breaker.py`), deliberately *not* a reuse of `GEMINI_CIRCUIT_BREAKER` — re-ranking's much stricter timeout budget would otherwise trip more often than extraction/policy evaluation's own real failure rate even when Gemini is perfectly healthy, spuriously degrading something load-bearing (contract analysis) because of something optional (search ordering).
- **A real bug found live, writing this module's own tests**: the initial `RERANKER_TIMEOUT_SECONDS = 4.0` caused every real call to fail outright — Gemini's real API rejects any deadline under 10 seconds (`"Manually set deadline 4s is too short. Minimum allowed deadline is 10s."`, a genuine `400 INVALID_ARGUMENT`, not a timeout). Fixed to `12.0`, with margin above the real discovered floor. Caught before this ever reached production, by the same test-writing discipline that's caught real bugs elsewhere in this engagement (§13's `pyotp.TOTP.at()` finding is the closest precedent).
- **Graceful degradation on any failure** (circuit open, timeout, malformed response, no candidates configured) — falls back to the original unranked order, truncated to the same page size; search never hard-fails because re-ranking failed.
- **One batched call, never one call per candidate.**
- **Never trusts an LLM-returned candidate index without checking it against the real input list** — the same discipline as offset re-verification (`_find_span`) and `rule_id` verification (`policy_evaluation_service.py`): a hallucinated out-of-range index is discarded and logged, not indexed into; a candidate the model silently omits from its response keeps its original relative position rather than being dropped.
- `@track_latency("search_reranking")` and `LLMUsageTracker.record_call("search_reranking", ...)` — real p50/p95 latency and real cost now show up in `/metrics`/`/api/monitoring/llm-usage` exactly like every other Gemini call, not a blind spot.
- Explainability: every result carries `original_rank`/`reranked_rank`/`relevance_score`; `search_metadata` carries a `reranking: {applied, reason}` block, so a caller can tell "re-ranking wasn't attempted" from "it ran and this is genuinely the best order" — matching this system's broader explainability discipline (grounding badges, `clause_id` traceability, learned-risk-adjustment callouts).
- **Caching, and a second real gap found while wiring it**: `EnhancedSearchService.search()` — the real REST path — had **no caching at all** before this (the parallel, LangChain-tool-facing `get_contracts_multi_level` path already did; this one never had it wired in). Now cached through the same `"vector_search"` TTL bucket, tenant-scoped key, keyed additionally on `RERANKING_ENABLED` so flipping the flag never serves a stale cached order from the other setting, and deliberately never caching a transient failure (each strategy's own except-path degrades to `search_metadata={"error": ...}` rather than raising — caching that would hide a real subsequent success behind a cached error for the whole TTL window).
- `RERANKING_ENABLED` (`Phase3Config`, default `false`) gates both the wider Cypher pool and the re-ranking call itself.

### Test suite

Unit-level (`test_reranker_service.py`, 12 tests): re-ranking measurably changes order in a constructed disagreement case (a candidate ranked last by original order promoted to first by relevance score) with exactly one batched call; graceful degradation on an LLM exception, a malformed response, no LLM configured, and empty candidates; the real circuit-breaker pattern (`test_circuit_breaker_wiring.py`'s established shape: fresh low-threshold breaker, repeated failures stop reaching the LLM, confirmed independent of `GEMINI_CIRCUIT_BREAKER`); real timeout enforcement (a simulated slow call falls back in under a second, plus a direct assertion the constructed LLM client's own `timeout` matches `RERANKER_TIMEOUT_SECONDS`); a hallucinated out-of-range index discarded without crashing; a response that silently omits some candidates keeping them in original relative order.

Integration-level (`test_search_reranking_integration.py`, 7 tests): the re-ranker only ever receives the calling tenant's own candidates, and two different tenants never see each other's re-ranked results; the feature flag genuinely gates old vs. new behavior (off: no `reranking` metadata, no LLM call, Cypher page size stays 10; on: metadata present, LLM called once, Cypher page size widens to 30; on but no query text: still no LLM call, since there's nothing to judge relevance against); cache hit/miss including a tenant-scoping proof (two tenants asking the identical query text must not share a cache entry).

No local-cross-encoder resource-fit test, since that approach was rejected by the measurement above, not shipped — building a test for code that doesn't exist would be pure waste.

Full suite: 579 passed / 1 skipped / 0 failed (up from 560 before this section's two commits).

## 19. Closing the `correlation_id`/MCP gap: a real in-process call path, not just a capability

§4 item 15/§8 had flagged this precisely: all 4 real MCP tool functions (`backend/mcp_server.py`) already accepted an optional `correlation_id`, but nothing in this codebase called from FastAPI into the MCP server in-process — the capability existed with no call chain to exercise it. This closes that gap for real, with a genuine new architectural call path, not a wire-up of something already half-built.

### The integration point, chosen deliberately

The MCP server exposes 4 tools genuinely distinct from what Contract Chat's existing 2 tools (`ContractSearchTool`, `EnhancedContractSearchTool` — contract/clause vector search) do: policy/playbook clause-library search (`PolicyRepository.search_policies_semantic`), playbook rule lookup (`PolicyRepository.get_applicable_policies`), precedent-clause search (`EnhancedPrecedentMatcherTool`), and contract-metadata fetch (`Neo4jContractRepository.get_contract_by_id`) — confirmed by import graph: none of that business logic was reachable from `contract_chat_agent.py` before this change. So the 4 real MCP tools were bound into Contract Chat's tool set *additively*, alongside the existing 2 — a genuine capability add for the chat feature (a user can now ask "what's our playbook rule for indemnification?" and get a real answer), not tracing infrastructure bolted onto an invented use case.

### The in-process call path itself

`backend/mcp/client_bridge.py`: `fastmcp.Client(mcp_server)` (the same `FastMCP` instance `backend/mcp_server.py` already builds) auto-detects a live server object via `fastmcp.client.transports.inference.infer_transport` and wires to it over an in-memory transport (anyio streams, no subprocess, no socket) — the real MCP protocol, in the same process, with zero new dependencies (`mcp==1.29.0`/`fastmcp==3.4.0` were already pinned; the in-memory transport is a documented, purpose-built feature of both). `call_mcp_tool_sync` is the entry point LangChain's synchronous `_run` calls into (matching `contract_chat_agent.py`'s existing `tool._run(**args)` convention); `call_mcp_tool` is its async counterpart. The standalone `python backend/mcp_server.py` stdio process remains untouched and still serves external MCP clients — this is a second, additional way to reach the same tool definitions, not a replacement.

`correlation_id` threading deliberately does **not** rely on `correlation_id_var` (the contextvar `TracingMiddleware` already populates) being read inside the tool's `_run`: LangGraph may execute sync nodes like `execute_tools` in a worker thread, and a contextvar set in the request's own coroutine isn't guaranteed to survive into a different thread. Instead it's threaded explicitly through `config["configurable"]` — `main.py`'s `runner()` now sets `correlation_id: corr_id` alongside the existing `tenant_id`, `execute_tools` reads both and injects them directly into the 4 MCP-backed tools' args (never `tenant_id` or `correlation_id` as LLM-visible schema fields, matching the existing tenant-isolation convention `test_chat_tenant_isolation.py` already proved for the original 2 tools) — the same explicit-config pattern already proven reliable for `tenant_id`, extended rather than reinvented.

### A real, reproducible bug found live during testing — and confirmed NOT a production issue

Writing the bridge's tests surfaced a real hang: calling the same in-process `FastMCP` server instance from a second `unittest.IsolatedAsyncioTestCase` test method (a fresh event loop per test, same shared server singleton) spun `fastmcp`'s in-memory session machinery into unbounded memory growth (2GB+, still climbing) around a `datetime.utcnow()` `DeprecationWarning` inside `mcp.server.lowlevel.server`. Root-caused by isolating variables one at a time rather than guessing: a plain script issuing repeated `asyncio.run()` calls against the same server singleton — the *actual* production pattern (`call_mcp_tool_sync` creates and fully tears down a fresh event loop per call) — completed cleanly across 3 sequential real calls with no growth. The real trigger was pytest's warnings plugin resetting the filter to "always" per test, turning a normally-deduplicated, harmless third-party deprecation warning into a per-iteration cost multiplier severe enough to look like an infinite loop. Fixed with a scoped `pytest.mark.filterwarnings("ignore::DeprecationWarning")` on the two new test files, not a global suppression, and a regression test (`test_repeated_sequential_sync_calls_do_not_hang_or_degrade`) that exercises the exact call pattern production actually uses.

### Test suite

13 new tests across two files. `test_mcp_client_bridge.py`: a real in-process call reaches the real tool function (only the bottom-most repository call mocked, same pattern `test_mcp_capabilities.py` already uses); the core proof this feature needs to exist at all — a caller-supplied `correlation_id` genuinely reaches the real `@mcp.tool()`-wrapped function's execution and shows up in its real log output (`self.assertLogs`, asserting on the actual `trace_id` field of the captured log record, not just that the call returned); graceful degradation (never raises) on a transport-level connection failure and an unknown tool name; the repeated-sequential-calls regression test above; sync-wrapper correctness both with and without an already-running event loop in the caller's thread. `test_mcp_chat_tools_end_to_end.py`: drives the real compiled LangGraph agent with a fake LLM (same pattern as `test_chat_tenant_isolation.py`) through a real in-process MCP call end to end, asserting the real repository received the real authenticated `tenant_id`; an LLM trying to smuggle a different `tenant_id`/`correlation_id` into the tool-call args has no effect (neither is a schema field); an MCP-side failure degrades the chat turn to a structured error message rather than crashing it. Two real bugs found and fixed while writing these tests: the bridge's fallback payload used an inconsistent `"raw"` key instead of `"error"` for non-JSON tool-error strings; a test patched `backend.mcp.client_bridge.call_mcp_tool_sync` when `langchain_tools.py` had already imported it into its own module namespace — the classic Python mocking gotcha (same class of bug the re-ranking work's tests hit, §18) — silently not testing anything until the log output made the real call visible. Full suite: 598 passed / 1 skipped / 0 failed (up from 585 before this section's tests).

### Live verification

Real docker-compose stack, rebuilt and restarted with this code. A real HTTP request to `/api/run/` with a genuine JWT (real `tenant_id`), a real `X-Correlation-ID` header, and a prompt nudging toward the new capability — the real Gemini model (`gemini-2.5-flash`) genuinely chose to call `PlaybookRuleLookup` on its own (not forced), and the real container logs show the same correlation id spanning the whole chain: `TracingMiddleware`'s "Handling incoming request" → RBAC/prompt-guard checks → `"[TraceID: <the-real-correlation-id>] - Executing tool get_playbook_rule for tenant <the-real-tenant-id>"` → a real `AuditLogger` entry (`"Audit logged: analysis_request - get_playbook_rule - success"`), genuinely persisted, not just logged. One id, chosen outside the process, traced through HTTP middleware, LangGraph config, the in-process MCP protocol call, and into the real MCP tool's own execution and audit trail.

## 20. Extending re-ranking to the remaining search levels and the tool-facing path

§18's re-ranking build covered `search_strategies.py`'s `DocumentSearchStrategy`/`ClauseSearchStrategy` and explicitly deferred the rest (`docs/DEMO_UNDERSTANDING.md` §8's item on this). This closes that gap: `SectionSearchStrategy`/`RelationshipSearchStrategy` (the same REST file), and separately, `enhanced_contract_search_tool.py`'s `get_contracts_multi_level` (the LangChain-tool-facing path used by `EnhancedContractSearchTool`/Contract Chat).

### The design question, answered before writing code

Asked directly: should the tool-facing path be consolidated into `search_strategies.py`/`EnhancedSearchService` instead of getting its own re-ranking wiring, to stop two implementations of "search with re-ranking" from drifting further apart? Investigated rather than assumed either answer. The two implementations had **already diverged in real, load-bearing ways before this pass, not just duplicated the same logic in two files**: different similarity thresholds (REST's `score > 0.3` vs. the tool-facing path's `score > 0.8` on every level — a real precision/recall tradeoff difference, not a typo); real capability gaps in both directions (`SearchParams`, the REST path's params type, has no `governing_law`/`monetary_value`/`cypher_aggregation` fields the tool-facing path's document search supports; the REST path has no `CHUNK` or `ALL`-level search the tool-facing path supports); separate, independent caching schemes; different return contracts (`SearchResult` domain objects vs. raw Cypher-shaped dicts the LLM reads directly as tool-call output text). **Decision: keep them separate, wire re-ranking into both additively, preserving each one's existing behavior exactly.** Consolidating would require deciding a winner for each of those real differences under time pressure, with no test coverage of the consequences of that decision — a materially larger, riskier change than "add a re-ranking stage," and exactly the kind of rushed refactor a standing instruction to avoid regressions right before a demo argues against. Flagged as a real, separately-scoped next step (`docs/DEMO_UNDERSTANDING.md` §8) rather than silently left undocumented.

### The wiring itself

Both `SectionSearchStrategy`/`RelationshipSearchStrategy` gained the exact same treatment `DocumentSearchStrategy`/`ClauseSearchStrategy` already had: `_cypher_page_size`/`_maybe_rerank` (already-generic helpers, no changes needed) parameterize the Cypher `LIMIT` via `$page_size` instead of a hardcoded `[..10]`, widening to `RERANK_POOL_SIZE` only when the flag is on and a real query exists. `enhanced_contract_search_tool.py` got its own equivalent pair of helpers (`_cypher_page_size`/`_maybe_rerank`), adapted to this file's flat-kwargs calling convention rather than `SearchParams`/`SearchResult` — deliberately not sharing the REST path's helpers, matching the "keep them separate" decision above. Its `_multi_level_search_cache_key` gained a `reranking_enabled` field, the same requirement already applied to the REST path's cache key in §18, so flipping the flag can never serve a stale cached page from the other setting.

### Three real bugs found while wiring, not invented tests for their own sake

1. **A ciphertext-as-clause-content bug, the exact same class already fixed in §18.** `enhanced_contract_search_tool.py`'s `_search_clauses` returned `cl.content` raw from Cypher — never decrypted, even though `Clause.content` is encrypted at rest (the same fact §18 already established when fixing `ClauseSearchStrategy`'s identical bug). This path has been returning base64 ciphertext as "clause content" to Contract Chat. Re-ranking on top of this would score ciphertext against a real query - not just imprecise, silently meaningless. Fixed the same way §18 fixed it: decrypt before returning or re-ranking. (`SectionSearchStrategy`'s `s.content`/this file's `_search_sections` needed no equivalent fix - re-confirmed, not assumed from the Clause case, matching §18's own discipline.)
2. **A real graceful-degradation gap in `_maybe_rerank` itself - found by the new tests, not obvious from reading the code.** `RerankerService.rerank()` catches failures *inside* its own LLM call and degrades gracefully by design (`RerankOutcome.reranked=False`) - but `_maybe_rerank` called `RerankerService(get_reranker_llm())` with no try/except around the whole expression. If `get_reranker_llm()` (or `RerankerService.__init__`) itself raised - before `rerank()`'s own safety net ever exists - the exception would propagate uncaught and crash the entire search request. A test simulating exactly that (`get_reranker_llm` raising) caught it immediately: `AssertionError: 0 != 2`, the search had hard-failed instead of falling back. This gap existed in the **original** §18 wiring too (`DocumentSearchStrategy`/`ClauseSearchStrategy` use the identical `_maybe_rerank` helper), not something newly introduced - fixed in both files' `_maybe_rerank`, wrapping the full construct-and-call in `try/except`, falling back to unranked results with `{"applied": False, "reason": "error"}`, matching this feature's own stated contract ("search must never hard-fail because re-ranking failed").
3. **A real, pre-existing crash found during live verification through Contract Chat itself, unrelated to re-ranking - `search_level.value` on a plain `str`.** `EnhancedContractSearchTool` is tenant-scoped, so `contract_chat_agent.py`'s `execute_tools` calls `tool._run(**args)` directly with the LLM's raw tool-call args (the same bypass that keeps `tenant_id` un-spoofable, `test_chat_tenant_isolation.py`) - deliberately skipping `args_schema`'s pydantic validation, which is normally what coerces a JSON string like `"document"` into the real `SearchLevel` enum. `_multi_level_search_cache_key`'s `search_level.value` assumed the enum and crashed with `AttributeError: 'str' object has no attribute 'value'` the moment a real Gemini tool call specified an explicit `search_level` - reproduced live with a real HTTP request through the real container (`ExceptionGroup` in the ASGI stack, `500`). This bug predates tonight's work entirely (the `.value` access was already there; this section only added one new key to the same dict) and has likely been breaking Contract Chat's multi-level search in both local dev and production whenever the model specified a level explicitly, not just when re-ranking is involved - found only because tonight's live-verification step happened to exercise this exact path. Fixed by normalizing `search_level` to the real enum once at the top of `get_contracts_multi_level` (`SearchLevel(search_level)` if not already an instance) - the existing dispatch logic (`search_level == SearchLevel.X`) already worked either way since `SearchLevel` is a `str` `Enum`, so only the `.value` access needed the fix. Live-reverified after the fix: the identical real Gemini tool call (`{"search_level": "document", ...}`) now completes cleanly end to end.

### Test suite

15 new tests, `test_search_reranking_extended_levels.py`. Part 1 (`search_strategies.py`): re-ranking measurably changes order for both `SectionSearchStrategy` and `RelationshipSearchStrategy` (a constructed 2-candidate disagreement case, same shape as §18's original order-change test); flag-off leaves both strategies byte-for-byte unchanged (no LLM call, no `reranking` metadata key); flag-on-but-no-query doesn't engage; graceful degradation on a simulated `get_reranker_llm` failure (bug #2 above, git-stash-verified to fail pre-fix); tenant isolation (the re-ranker only ever receives the calling tenant's own candidates). Part 2 (`enhanced_contract_search_tool.py`): the same order-change/flag-gating/degradation/tenant-isolation shape across all 4 newly-wired levels via a single fake graph dispatching on Cypher RETURN-clause shape; a dedicated regression test for the ciphertext bug (bug #1) - seeds real `field_encryptor`-encrypted content (not a plaintext stand-in), asserts the reranker's candidates and the final returned content are both genuinely decrypted, in both flag-on and flag-off configurations; a cache-key test proving `RERANKING_ENABLED`'s state alone changes the computed key; a regression test for bug #3 - calls `get_contracts_multi_level` with a plain `str` `search_level` (no LLM involved) and confirms no crash. Full suite: 613 passed / 1 skipped / 0 failed (up from 598 before this section, per §19).
